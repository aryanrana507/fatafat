## Security Admin Panel (2026-11-20, user: "bhai secourty admin pannel" + "what if someone hacks it")
- **Admin login**: separate Admin Panel entry (footer + Profile). Default admin PIN **1114** (user changed it from the originally proposed 1234 to 1114 in a follow-up message). The PIN is stored ONLY as a salted SHA-256 hash (`admin_config` table: pin_hash + salt + failed_attempts + locked_until) and verified by the `adminLogin` server action — never in client code. 5 wrong tries → login locks for 5 minutes; every failed/blocked attempt is written to `admin_activity` with timestamp. Success issues a random session token (`admin_sessions`); every admin action re-validates it server-side via `requireAdmin`, which slides expiry — **30 minutes of inactivity auto-expires the session**. Changing the PIN (Settings, current PIN required) re-salts/re-hashes and deletes ALL sessions, forcing fresh login.
- **Admin sections** (all token-gated actions): Dashboard (revenue/orders/products/vendors/low-stock from real DB), Products (search, edit name/price/MRP/stock, add, delete — logged), Orders (all accounts, item details, direct status set incl. cancel with stock+coin restore — logged), Vendors (approve/remove; remove deletes their catalog products), Coupons (platform coupons are now DB rows in `platform_coupons`; enable/disable/delete for platform + vendor coupons — `validateCoupon`/`placeOrder` share one `findCoupon` lookup so toggles apply instantly), Customers (accounts + per-account orders/spend + coin balances), Support (help-page tickets, resolve/reopen), Activity Log (login success/failed/locked, product/order/coupon/settings/PIN/backup events with times), Settings (delivery charge, free-delivery threshold, geofence km in `app_settings` — read live by `placeOrder` fee math + geofence check and by `getBootstrap` area serviceability; plus Change PIN and **Data Backup** — `adminBackup` returns a JSON export of products, orders, vendors, platform+vendor coupons, sanitized accounts (no PIN hashes), support tickets and settings, downloaded client-side).
- **Money math**: all prices/totals/discounts/coins are computed server-side from DB rows in `placeOrder` (client sends only product ids + quantities); confirmed and kept as the invariant.
- **Role separation**: customer UI exposes no admin controls; the Admin Panel renders only a PIN screen without a session, and every `admin*` action rejects invalid/expired tokens with a session-expired error the client turns back into the login screen.
- **Partner vendors**: the catalog's three built-in partner stores (Sharma General Store, Gupta Snacks Corner, City Care Store — names carried on product rows since the original hybrid build) are seeded as real `vendors` rows by `ensurePartnerVendors` (only while the vendors table is empty and only for names products actually reference), so the admin dashboard count and Vendors tab match the storefront; self-onboarded vendors append as their own rows. The default PIN value is never rendered anywhere in the client UI.

## Customer Accounts + Help Page (2026-11-20, user follow-up)
- **Accounts**: `accounts` table (name, phone, salted PIN hash, lockout fields, referral code, coins, current area). The legacy demo profile becomes **guest account id 1** (created by `ensureAccounts` from the profile row; its existing orders/coins/subscriptions/addresses carry `account_id = 1` via migration defaults — data untouched). Orders, subscriptions, coin ledger, addresses, wishlist and notify-me all gained `account_id` (wishlist/notify-me rebuilt with composite PKs). A single-row `app_state` pointer names the active account; login moves it, logout returns it to guest — every customer action resolves its account through `currentContext`, so each account sees only its own orders/coins/wallet/subscriptions/addresses/referral code.
- **Sign-up** (`customerSignup`): name + mobile (+91/0 prefixes normalized like checkout) + 4–6 digit PIN, hashed server-side; duplicate mobile rejected with a clear error — except the guest number with no PIN yet, which is *claimed* by setting its PIN (data stays attached). **Login** (`customerLogin`): server-verified, per-account 5-try/5-minute lockout, attempts also written to the admin activity log. Sessions are random tokens in `customer_sessions` (30-day expiry); the client keeps its token in localStorage and validates it on start via `customerSessionCheck`. **Logout** in Profile deletes the session and restores the guest account.
- **Help page**: FAQ accordion (order kaise kare, delivery time, payment options, cancel/refund, coins, subscription band karna, area radius), tappable Call / WhatsApp / Email contact buttons, and a "Problem batao" form (`submitSupportTicket` → `support_tickets` table + staff notification). Tickets appear in the Admin Panel's Support tab where the admin can call the customer and mark them resolved/reopen (`adminListTickets` / `adminSetTicketStatus`, logged). The FAQ and login screen honestly state that OTP login arrives only when an SMS provider is connected — PIN login is the current secure method.

## Long-term data behavior
- **Loyalty features (added 2026-11-19, user said "kr do" to the recommended trio)**: (1) Refer & Earn — profile carries a server-generated referral code (`FF-<NAME>-<last4 phone>`); `applyReferralCode` credits the applier 50 Fatafat Coins once (guarded by `referred_by`), records a `coin_ledger` row and a customer notification, and notes the code owner also gets ₹50. (2) Subscriptions — `subscriptions` table (product, daily/weekly frequency, qty, active/paused/cancelled) created from the product sheet, managed in Profile → My Subscriptions via `createSubscription` / `setSubscriptionStatus`. (3) Fatafat Coins + Wallet — balance lives on `profile.coins`; every `coin_ledger` row is an auditable earn/redeem/referral/refund move. `placeOrder` accepts `use_coins`: redeem is capped at the payable amount (1 coin = ₹1) and the order earns floor(5% of final paid total) coins; orders store `coins_redeemed`/`coins_earned`; cancelling an order refunds redeemed coins and claws back earned ones (floored at 0).
- **Refresh policy**: No scheduled refresh. Products/stock/orders/notifications are live DB state; the client polls bootstrap/orders/notifications every ~8s via react-query so staff-panel status changes and stock decrements appear without reload. Catalog seeding is idempotent and never overwrites existing rows or user edits.
- **Growth**: Orders, notifications, and addresses grow as the user places orders / adds addresses; products stay a fixed 24-row catalog whose stock mutates. Wishlist rows toggle per product.
- **Ordering**: Products by catalog order; orders and notifications newest first.
- **Time semantics**: Order created_at stored as timestamp_ms; tracking progress derives from elapsed real time since creation plus staff advances; rendered viewer-local.

- **Tried**: Hand-drawn SVG/CSS map for live tracking
  **Why rejected**: Artifact rules forbid hand-authored maps/route schematics; tracking is delivered as a live status timeline with ETA countdown, distance-remaining and rider card, polled from the server.
